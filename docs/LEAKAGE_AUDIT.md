# Leakage audit: is every feature knowable *before* the churn window? (B-21)

An early-warning product only works if every number the model reads was already
true when the prediction window opened. A feature that moves *during* the window
it is supposed to predict makes the metrics look good and the product useless: the
model reports the past instead of warning about the future.

This page audits all 24 columns `config.FEATURES` carried before B-21, states a
verdict per column, and gives the measurement behind it. The measurements live in
[`feature_set_comparison.json`](feature_set_comparison.json), regenerated by
`python scripts/compare_feature_sets.py`.

**Outcome:** three columns dropped (two reverse-causal, one redundant), twelve
flagged as needing a lag we cannot verify on this data, nine clean. Test PR-AUC
fell from 0.520 to 0.369 and precision@20 from 0.75 to 0.35. **That drop is the
result, not a regression** — see "What to say about the lower numbers".

> Everything here is measured on `data/mentorluk_churn_veriseti.csv`, a **synthetic
> single snapshot**: one row per student, no as-of date, no history, and no written
> definition of the window `churn` is observed over. That last gap is the reason
> several verdicts below are "lagged-needed" rather than "safe" or "reverse-causal":
> for those columns the question is answerable only from a real client's export.

---

## The window problem, stated once

The label `churn` is observed over some window of length *W*. Every feature must
be read at the window's **start**. In this file features and label sit in the same
row with no timestamps, so for any column that is a *trailing aggregate* we cannot
tell whether its trailing period ends before the window opens or runs through it.

`CHURN_WINDOW_DAYS = 30` in `config.py` is a **stated assumption** used to size the
lag mechanism. It is not a measured property of this dataset.

## Verdicts

Verdict meanings:

| verdict | meaning |
|---|---|
| **safe** | static, or forward-looking, or a monotone clock — its value at the window start is either the same or trivially recoverable |
| **lagged-needed** | a trailing aggregate whose period may overlap the window. Kept, because it is student-side behaviour and dropping all twelve leaves no model at all — but a real client export must state the as-of date, and until then no per-feature claim is defensible |
| **reverse-causal** | measures a break-off that has **already happened**, and/or degrades as the product is used correctly. **Dropped.** |
| **redundant** | adds nothing over a column already present. **Dropped.** |

`auc` below is the univariate ROC-AUC of that single column against `churn`,
direction-corrected (0.500 = no signal). It is what the column knows on its own.

## What it costs: measured

Six feature sets, each trained through the **real** `pipeline/training_pipeline.py`
into a temporary directory, same split (`random_state=42`), same 3384 training
rows, evaluated once on the same 677-row test set (base churn rate 0.272).
Regenerate with `python scripts/compare_feature_sets.py`; the numbers below are
read from [`feature_set_comparison.json`](feature_set_comparison.json).

| feature set | n | ROC-AUC | PR-AUC | logreg PR-AUC | CV ROC | threshold | precision@20 | lift@20 | flagged |
|---|---|---|---|---|---|---|---|---|---|
| full (pre-audit) | 24 | 0.718 | **0.520** | 0.537 | 0.743 | 0.31 | **0.750** | 2.76 | 217 |
| without the two contact columns | 22 | 0.603 | 0.376 | 0.379 | 0.646 | 0.31 | 0.500 | 1.84 | 214 |
| only the contact columns + categoricals | 7 | 0.712 | 0.504 | 0.506 | 0.702 | 0.31 | 0.700 | 2.58 | 208 |
| **single column `days_since_last_contact`** | 1 | 0.678 | 0.478 | 0.486 | 0.655 | 0.22 | **0.900** | 3.31 | 291 |
| only `days_to_next_exam` removed | 23 | 0.715 | 0.506 | 0.537 | 0.739 | 0.27 | 0.750 | 2.76 | 262 |
| **post-fix (shipped)** | 21 | 0.600 | **0.369** | 0.379 | 0.640 | 0.29 | **0.350** | 1.29 | 265 |

Three things this table settles:

1. **The signal was in the two contact columns.** Removing them costs 0.144 PR-AUC
   (0.520 → 0.376); the other twenty-two columns together are worth 0.376. Seven
   columns that are *only* the contact pair plus the categoricals reach 0.504 —
   within 0.016 of the full model.
2. **One column beats the whole model where it matters.**
   `days_since_last_contact` alone gets **precision@20 = 0.900** against the
   24-feature model's 0.750. A model whose best feature outranks it at the top of
   the list is not adding intelligence, it is adding a wrapper.
3. **`days_to_next_exam` is free to remove.** Dropping only it moves PR-AUC 0.520
   → 0.506 and precision@20 not at all — inside the run-to-run noise of a column
   with univariate auc 0.500.

### precision@20 is twenty coin flips — a health warning

`PRECISION_AT_K = 20` describes the real workflow (a mentor works the top of the
list), but it is measured on twenty rows. The bootstrap intervals in
`feature_set_comparison.json` (2000 resamples of the test set) make the width
visible:

| feature set | P@20 (95% CI) | P@50 (95% CI) | P@100 (95% CI) |
|---|---|---|---|
| full (pre-audit) | 0.750 [0.450, 0.950] | 0.660 [0.520, 0.780] | 0.600 [0.510, 0.700] |
| post-fix (shipped) | 0.350 [0.150, 0.600] | 0.520 [0.380, 0.660] | 0.480 [0.370, 0.570] |

**`0.75 → 0.35` at k = 20 is eight students, and the two intervals overlap.** The
honest headline for the shipped model is the top-50 number: **precision@50 = 0.52
[0.38, 0.66] against a 0.272 base rate — a 1.9× lift**, with a band narrow enough
to quote. `PRECISION_AT_K` is left at 20 because that is the mentor capacity the
product is built around; this is a note about how much weight the number carries,
not a reason to change it.

### One thing that got better

Before the audit, every at-risk student's SHAP explanation was led by
`mentor_contact_freq_per_month`, with `days_since_last_contact` usually second — so
the daily message told every mentor the same thing, which is a message with no
information in it. On the same 25-row demo export, the post-audit model's top three
students are now led by three different features:

```
STU300016  message_response_time_hours (+0.18), trial_exam_score_trend (+0.17), payment_delay_days_avg (+0.15)
STU300025  satisfaction_survey_score (+0.28), message_response_time_hours (+0.27), payment_delay_days_avg (-0.18)
STU300012  program_adherence_rate (+0.33), message_response_time_hours (+0.24), payment_delay_days_avg (-0.19)
```

This was previously written up as impossible ("dropping those columns does not
diversify the explanations, it destroys the model"). Both turned out to be true at
once: the model is weaker *and* the explanations are per-student. A mentor can act
on "adherence is down"; nobody can act on "you have not called them".

## The lag mechanism, and what it can and cannot do here

`src/data/features.apply_contact_lag()` + `config.CONTACT_LAG_DAYS`.

**What it does.** With `CONTACT_LAG_DAYS > 0`, every contact column that is in
`config.FEATURES` must arrive with a companion column carrying its value as of the
window start — `days_since_last_contact_at_window_start`,
`mentor_contact_freq_per_month_at_window_start`. That value replaces the
scoring-time one and the companion column is removed, so the frame stays exactly
the feature set. It runs in both `build_training_frame` and `build_serving_frame`,
so training and serving cannot disagree.

**What it refuses to do.** If the lag is switched on and a companion column is
missing, it **raises**. It does not fall back to the scoring-time value. A lag that
silently did not happen is worse than no lag, because then the metrics look like a
fixed model.

**Why it is off in this repo, and why that is honest.** Nothing in
`apply_contact_lag` subtracts `CONTACT_LAG_DAYS` from anything, because on a single
snapshot there is nothing valid to subtract:

- `days_since_last_contact` — the arithmetic reconstruction is
  `value_at_window_start = value_now − W`, and it is only valid when no contact
  happened inside the window, i.e. when `value_now ≥ W`. Measured: at *W* = 30 that
  holds for **8.8%** of rows. For the other 91.2% the pre-window value is censored
  — *some* number ≥ 0 that the snapshot does not contain. Shifting the 8.8% and
  inventing the rest would be a fabricated column, so it is not implemented.
- `mentor_contact_freq_per_month` — a single trailing-30-day rate. There is no
  arithmetic that removes the window's contacts from one aggregate number. Not
  reconstructable at all, at any window length.

So on this dataset the two columns are **dropped**
(`config.AUDITED_OUT_FEATURES`), not lagged, and `CONTACT_LAG_DAYS` stays 0.

**Real vs scaffolding, stated plainly:**

| | status |
|---|---|
| the three dropped columns, and the numbers in this document | **real** — measured on the data in `data/` |
| `apply_contact_lag` mechanism, config switch, its refusal behaviour, its tests | **real code, unexercised path** — correct and tested, but no row in this repo ever takes it |
| any claim that the contact columns *can* be used safely | **not established** — it needs a client export with a window-start value per row |

**Turning it on for a client.** Three edits, no new code:

1. their export adds `days_since_last_contact_at_window_start` (and/or
   `mentor_contact_freq_per_month_at_window_start`), computed on their side from
   their own contact history;
2. put the column names back into `config.FEATURES` — their `FEATURE_BOUNDS`,
   `INTEGER_FEATURES` and `FEATURE_LABELS` entries were deliberately left in place,
   and `config.AUDITED_OUT_FEATURES` must drop the names it no longer parks;
3. set `CONTACT_LAG_DAYS` to the client's real window (`CHURN_WINDOW_DAYS`).

Then re-run `scripts/compare_feature_sets.py`. If the lagged columns still carry
most of the signal, that is a *finding* rather than a leak — but it has to be
measured with the lag in place, which this dataset cannot do.

## Follow-ups this audit did not fix

- **`UNIMPUTABLE_REQUIRED` still drops rows on `mentor_contact_freq_per_month`.**
  Training loses 45 rows (3429 → 3384) over a column the model no longer reads.
  Left as-is on purpose so the before/after table above compares two models on the
  identical 3384 rows; worth removing separately, at which point every number in
  this document has to be re-measured.
- **The twelve "lagged-needed" columns are unresolved by construction.** They stay
  in the model. The claim this audit supports is "no column is *known* to be
  reverse-causal any more", not "no column is". Resolving them needs an as-of date
  per column in a real export — which is also what B-03 (`daily_students.as_of_date`)
  is for.
- **`parent_involvement` is the one to watch.** It is a human judgement with no
  timestamp, and a mentor's assessment of a family is exactly the kind of field
  that gets updated *because* a student is drifting.
- **`missed_trial_exam_count` and `payment_delay_days_avg` are the near-label
  pair.** If a client's churn definition is "stopped paying" or "stopped
  attending", these two are partly the label. Check the label definition before
  quoting anything about them.

## What to say about the lower numbers

- The old numbers were mostly one column, `days_since_last_contact`, and that
  column records what the *mentor* did. A mentor stops calling a student who has
  stopped answering, so it partly measures a break-off that has already happened —
  and it flattens across the whole cohort as soon as a client runs a regular
  contact policy, which is to say the old model got worse exactly as the product
  was used properly.
- The current model reads only student behaviour. On synthetic data that is
  **precision@50 = 0.52 against a 0.272 base rate, a 1.9× lift**: weaker than the
  old 0.75, and it is the first number here that would survive a customer's own
  audit.
- It is still synthetic data. The number to promise a pilot is the *method* — this
  audit, run again on their export, with their window written down — not this
  figure.
